# InReel Deflection System — 3D Model / CAD

Mechanical CAD for the deflection (gimbal) system on Sandvik's electrified rotary drill rigs. Companion repo to the firmware/control-logic repo (`Sandvik-Common/dri`), split out because CAD assets (STEP/STL exports) don't belong version-controlled alongside code.

## Scope

Two-axis gimbal that measures cable angle deviation and feeds the cable reel control loop. This repo covers the mechanical yoke/mounting design; encoder signal processing and control logic live in `dri`.

Both pairs run along native X. Nice cross-check: this pair's midpoint X (7.1061) and fixed Y (7.4432) both match axis-0's numbers exactly, confirming both axes truly intersect at one consistent point, `NATIVE_PIVOT = {x:7.1061, y:7.4432, z:1.5000}` (fully exact now, not an estimate on any axis).

Unlike axis-0, this pair has a much bigger span mismatch: inner yoke's stub-to-stub span is 15.40in, outer yoke's hole-to-hole span is 12.00in — a 3.40in difference. **Frame orientation (up/down flip, then 90° yaw) — visually confirmed correct by the user**, but the yaw fix (`rotateY90`) was later found to be a real bug — see below.

**Which slider drives which rotation.** Briefly swapped (X/Y ↔ innerGroup/outerGroup), then reverted ("the axes are not correct") — the original assignment stands: **Axis 0/X drives `outerGroup`** (frame↔outer_yoke), **Axis 1/Y drives `innerGroup`** (outer_yoke↔inner_yoke).

**Bug found and fixed: `rotateY90` was breaking the frame connection (2026-07-23).** The 90° yaw fix mentioned above swapped simX/simZ *after* the native→sim mapping — which silently moved axis-0 (the frame↔outer_yoke shaft-hole line) off of world Z, the axis `outerGroup` actually rotates about. Verified directly against the live deployed function (not a reimplementation — that's exactly what missed this the first time): with `rotateY90`, axis-0's points came out at `simX≈±0.247` (varying), `simY≈0`, `simZ≈0` — sitting on the **X** axis, not Z. Since frame is static (added to `scene`, never rotates) and outer_yoke's shaft-hole needs to stay coincident with frame's leg-hole as Axis 0 changes, this meant the connection would visibly separate as soon as the X slider moved away from 0 — invisible in a static screenshot, but real.

Fixed with a proper replacement, `axis1Vertical`, instead of patching `rotateY90` further: it leaves native Y → simZ **untouched** (axis-0 stays exactly on Z, unaffected — frame's `rotateY90` was removed entirely, back to its original formula), and re-routes native X (axis-1's varying direction, per the user: *"the inner yoke needs the pivots lined up on the Y axis"*) to simY instead of simX — putting the outer_yoke↔inner_yoke pivot on the **vertical** axis. `innerGroup`'s rotation was changed from local-X to local-Y to match. Both are proper rotations (det=+1 in each case), not mirrors.

Verified against the live deployed function for all 4 relevant points at once: frame's axis-0 lands at world `(0, 0.75, ±0.241)`; outer_yoke's axis-0 lands at local `(0, 0, ±0.247)` (same line, once `outerGroup`'s position is added — connects to frame); outer_yoke's axis-1 lands at local `(0, ±0.152, 0)`; inner_yoke's stub lands at local `(0, ±0.196, 0)` (same line as outer_yoke's axis-1 — connects). The small residuals present (~6.4mm axis-0, ~43mm axis-1) are exactly the previously-disclosed span-mismatch amounts from the exact-coordinate section above, not new errors.

**Facing direction restored with `rotateY180` (not `rotateY90`).** Removing `rotateY90` fixed the connection bug above, but it also removed the yaw correction it had accidentally been providing — the gimbal needed to face away from the rig again. A 90° yaw is exactly what broke axis-0 (it moves the Z-axis onto the X-axis); a **180°** yaw about sim-up does not: `Ry(180)` is `(simX,simY,simZ)→(-simX,simY,-simZ)`, which maps the Z-axis to itself (sign-flipped) and the Y-axis to itself too — both pivot alignments survive it exactly (proper rotation, det=+1). Applied to frame and outer_yoke only (matching each other, as before); verified the same way — all four pivot points land at the same X/Y/Z magnitudes as before `rotateY180`, just with axis-0's Z-values sign-flipped as expected, connections intact.

**Slider assignment re-swapped to match the written requirements doc (2026-07-24).** A formal requirements doc now serves as the authoritative spec, and it states "the inner yoke represents the x-axis of the deflection" / "the outer yoke represents the y-axis". The deployed code contradicted this, so the assignment was swapped (after explicitly confirming, since this same swap had been made and reverted once before): **Axis 0/X drives `innerGroup`**, **Axis 1/Y drives `outerGroup`** — the opposite of the line above, which is now superseded.

**Cable was frozen on the rotation axis (2026-07-24).** The cable/hub/dragHandle all sat at `innerGroup`'s local origin — which, after `axis1Vertical` moved axis-1 to vertical, *is* `innerGroup`'s rotation axis. Rotating about an axis never moves points lying on it, so the X slider visibly did nothing (a pendulum spun along its own string). Fixed by anchoring them at the real tube-exit point read directly off the loaded `inner_yoke` mesh's local bounding box, rather than an arbitrary offset. The drag-to-rotate inverse-kinematics further down assumed the cable hangs from the exact origin, so it's now only an approximation — not re-derived, since the requirements call for slider + tension control, not drag.

**Whole-assembly 90° yaw: `rotateY90` reintroduced, correctly this time (2026-07-24).** The mounting frame's legs needed to run along world X ("legs symmetric with the X axis") instead of along the toward/away-from-rig direction. A top-down render confirmed the real CAD frame is a symmetric rectangular ring whose leg spread *is* the physical pivot shaft line — so the frame can't be rotated alone without breaking the pivot. The fix is a single rigid yaw of the entire already-assembled unit: the same `Ry(90)` (`x'=z, z'=-x`, det=+1, applied post-mapping) is applied **uniformly to all three parts**. This is what the original iteration-3/4 `rotateY90` got wrong — that one was applied to only some parts, leaving them rotationally inconsistent, which is what broke axis-0.

Two dependent values must move in lockstep with the flag, or the connection breaks: `outerGroup`'s rotation axis (world Z → world **X**; `Ry(90)` applied to the old axis vector `(0,0,1)` gives exactly `(1,0,0)`), and the cable/hub/dragHandle offset (local X=+0.273 → local Z=−0.273; same rotation applied to the same point). `innerGroup`'s axis is untouched — Y is the yaw axis itself, invariant under a rotation about Y.

Verified in Python before touching the live JS: the top-down render after the yaw shows every pivot circle still coincident and the legs now spanning X; a numeric swing check confirmed Axis 1 (Y) still drives the cable tip toward more-negative Z (away from rig) as it increases, and Axis 0 (X) still produces pure lateral motion with Y/Z fixed — both matching the documented pre-existing behavior. `scripts/render_combined.py` carries the same `rotate_y90` flag so it stays in sync with the JS.

**Inner yoke stubs swapped to the opposite holes (2026-07-24).** `flip180Z` turned off on `inner_yoke`, so each male stub now mates into the *other* female hole. Verified against the exact CAD coordinates before changing: relative to the pivot, the female holes sit at ±0.1524 and the male stubs at ±0.1956 — with the flip on, `stub_L` sat on the same side as `hole_L`; with it off, `stub_L` lands at −0.1956, mating into `hole_R`. Nothing else moves (the mesh's local X and Z bbox ranges are identical either way, so the cable/hub/dragHandle stay aligned with the real tube end); only Y changes, which *is* the swap.

**Outer ring rotated onto the Y-axis: `rotateX90` (2026-07-24).** The outer yoke ring stood vertical, with the Y-axis (toward/away-from-rig) punching perpendicularly through it. Requested change: the ring's plane should *contain* that axis at zero deflection. Since a ring's plane contains both of its own pivot axes, this is a 90° rotation about axis-0 (world X) — the plane goes from X-up to X-Z, axis-0 stays exactly on X (frame connection untouched, and the frame must **not** get this flag), and axis-1 swings from vertical onto world Z. `Rx(-90)` (`y'=z, z'=-y`, det=+1) is used rather than `Rx(+90)` because it leaves the inner yoke's cable tube pointing **down** instead of up, so the cable still hangs below the gimbal.

Two dependent values move with it: `innerGroup`'s rotation axis (local Y → local **Z**, following axis-1), and the cable/hub/dragHandle anchor (local Z=−0.273 → local Y=−0.273, following the tube end — confirmed against the loaded mesh's bbox, where Y now reaches −0.2731, exactly the value Z used to reach). `outerGroup` stays on world X, since `rotateX90` is a rotation *about* that axis.

Verified before touching the live JS: both pivot axes still land on a single shared line (axis-0 at X=±0.241/±0.2474, axis-1 at Z=±0.1524/±0.1956 — the same two previously-disclosed residuals, no new error), and **both sliders were confirmed to still move the cable**, which is the specific failure mode that bit this file once already. Y swings the tip toward −Z (away from rig), X swings it toward +X (right = positive, per the requirements doc), and they compose correctly.

**Outer yoke turned right-side up: `rotateZ180` (2026-07-24).** With the ring horizontal, the model itself read upside down. Turning it over is a 180° rotation, and two of them do it — but they are **not** interchangeable here. `Rx(180)` (negates simY, simZ) would move axis-1's female holes from Z=−0.1524/+0.1524 to +0.1524/−0.1524, silently undoing the stub-to-hole pairing set by `flip180Z: false`. `Rz(180)` (negates simX, simY) leaves those holes exactly where they are — they sit at simX=simY=0, precisely the components it negates — and only mirrors axis-0's shafts along their own shared line. `Rz(180)` is therefore the correct choice; det=+1, applied last in sim space about the part's local origin. Verified after the change: axis-0 shafts still at X=±0.2474, axis-1 holes still at Z=∓0.1524 with the crossed pairing intact, the ring's Y range flipped, and Z unchanged so front/back orientation is preserved.

> Gotcha for `scripts/render_combined.py`: `world_y` must be **0** for the outer/inner yoke, matching the live JS, where those parts are children of `outerGroup`/`innerGroup` and take their height from `outerGroup.position.y`. Baking `PIVOT_Y` in before `rotate_x90` lets that rotation drag the height into Z. This was harmless for `rotate_y90` (which leaves Y alone) but is not for `rotate_x90` — add the height *after* the transform.

## Duty cycle override, and a 5 HP hydraulic motor test case (2026-07-27)

Two additions to the torque check panel above.

**"Test a specific duty cycle instead of the live one"** decouples the torque box from the sliders. Off (default), it reads whatever duty the reel-trim loop is actually producing, every frame. On, a 0–100% slider substitutes a manually chosen value instead, so you can ask "what would 50% duty do" without driving the encoders to whatever angle happens to produce it. Verified live: with the override at 40% and the sliders driven to a position that genuinely produces 12% duty in the real reel-trim loop, the torque box correctly held at 40% every frame, ignoring the live value entirely.

**"Load 5 HP hydraulic motor (illustrative)"** fills in a torque figure for a hydraulic motor rather than the electric-motor framing the panel started with. This matters for two real reasons, not just as another preset:

- Power alone doesn't give torque — converting needs a speed (`torque = power / ω`). No real hydraulic motor spec exists in this repo either, so the preset assumes an illustrative 500 RPM rated speed to get there: 5 HP = 3728.5 W, at 500 RPM (ω = 52.36 rad/s) → **~71.2 Nm**. That 500 RPM is flagged in the code and the UI as an assumption, not a datasheet number, same discipline as everywhere else values are estimated in this project.
- **Hydraulic motors don't have back-EMF.** The whole "torque tapers to zero at no-load speed" caveat from the earlier DC-motor discussion doesn't apply here — a hydraulic motor's torque stays roughly flat across its speed range, set mostly by system pressure rather than by a voltage/back-EMF balance. The `duty% × torque × ratio × efficiency` formula is still reused as a first-pass approximation, but its correctness now depends on a different, unconfirmed assumption: whether the real `DO_Motor_Wind`/`DO_Motor_Unwind` outputs actually drive the hydraulics through a time-proportioned valve (where duty ≈ average flow ≈ average torque, a reasonable approximation) or through something else entirely.

Verified: `HYDRAULIC_5HP_TORQUE_NM` computes to 71.209 Nm in the browser, matching the hand calculation exactly. At 75% test duty, default (electric) placeholder spec gives 956.25 Nm; loading the hydraulic preset at the same 75% gives 192.24 Nm — both match `duty × stall × ratio × eff` exactly, confirming the preset and the override compose correctly together.

## Motor & drum torque check (2026-07-27)

Follow-on to the tuning panel above. Fixing the scale and contribution factor means the reel *reports* a duty cycle at realistic deflection angles — but duty cycle isn't torque, and nothing in either repo confirms that duty actually moves the real drum. This panel makes that gap explicit rather than assuming it away.

**What's real:** drum inertia `I(L)`, ported directly from `scripts/reel_inertia_model.py` (the closed-form continuous-annulus approximation — cross-checked there against the discrete layer method to <0.1%). Same real geometry (62in core, 72.25in width, 72in flange) and real cable spec (Nexans 36-517-002). Verified the JS port against the Python reference values at three points (empty, half, full spool) — **0.000% difference** at all three; the constants are copied from a script run, not hand re-derived, so they won't drift.

**What's a placeholder:** motor stall torque, gear ratio, and drivetrain efficiency. No motor spec exists in either repo. Defaults are round illustrative numbers (50 Nm / 30:1 / 0.85), and the panel displays an explicit warning whenever those defaults are still in place, so the numbers can't be mistaken for real ones.

**The model:** a stall-torque approximation — `torque available = duty% × stall torque × gear ratio × efficiency` — deliberately simple (no back-EMF correction), since the question being asked is "can it start moving at all," not "what's its running speed." `angular acceleration = torque / I(L)`.

Example, at the defaults: 12% duty (X axis at its ±45° mechanical limit, default 0.12 contribution factor) against a half-wound drum (I ≈ 1771 kg·m²) gives 153 Nm available and 0.086 rad/s² (~0.8 RPM/s) — a real number now, but only as good as the placeholder motor spec feeding it. **This box does not say whether 12% duty is enough — it can't, until real motor numbers replace the placeholders.** That's the actual open question for the team, not something this sim can resolve on its own.

## P-control tuning panel, and why the reel never responded (2026-07-27)

The reel indicator was showing HOLD at every realistic deflection angle. The LEDs were fine — there was genuinely nothing to show. Two compounding problems:

**1. Scale mismatch.** `raw01perc` is `signedCounts * 1000 / 32768`, and 32768 counts is **180°** of encoder travel. So the ±1000 per-mille vector is calibrated for a half turn. The gimbal is mechanically hard-stopped at **±45°**, so the real mechanism only ever exercises the bottom quarter of that scale. At its 45° limit an axis reaches 250 of a possible 1000 per-mille; the rescale turns that into ~167, and the contribution into ~0.020 — five times under the 0.10 discard threshold. **No deadzone value fixes this**; raising the deadzone only shrinks the result further.

This also means the config numbers don't mean what people assume. At the 180° scale, the X deadzone of ±100 is **±18°**, and Y's ±350 is **±63°**.

**2. No headroom.** Contribution is `vector/1000 × 0.12`, tested against a 0.10 discard threshold — so output only exists above vector 833, the **top 17%** of the range, even once the scale is right.

Measured, via the panel's solver:

| Config | X axis | Y axis |
|---|---|---|
| Today's firmware (180°, 0.12) | needs 153° — **never responds at all** | from 160.5° (top 11%) |
| Scale fixed (45°, 0.12) | from 38.3° (top 15%) | from 40.1° (top 11%) |
| Scale + factor (45°, 0.5) | from 12.6° (**top 72%**) | from 21.6° (top 52%) |

**The panel** exposes full-scale deflection, both contribution factors, and the discard threshold as live controls, with a solver reporting the smallest angle on each axis that actually produces a reel command. Every deadzone field is now labelled with its equivalent in degrees at the current scale — the unlabelled per-mille is what made this hard to see.

`computeAxis()` takes `fullScaleDeg`, defaulting to 180 so **passing 180 reproduces the firmware exactly**. The UI defaults to 45 (the real mechanical travel) so the sim is useful out of the box; "Reset to today's firmware" restores 180 / 0.12 / 0.10 for side-by-side comparison. `raw01perc` is now clamped to ±1000, since nothing stops an axis being driven past its full-scale reference and an unclamped vector would break the per-mille contract.

Verified live at 45° scale with 0.5 factors: X=30° → vector 629, contribution 0.315, 31% duty, UNREEL. Y=−30° → vector −486, contribution −0.243, 24% duty, REEL IN. Rest → HOLD. All three states reachable at angles the gimbal can physically reach.

> None of this is changed in firmware — it's a simulator instrument for deciding what the config *should* be. The scale question in particular needs a decision before it goes near `cablereel_signals.xml`.

## Reel command indicator (2026-07-24)

The reel trim panel shows a three-state command — **UNREEL / REEL IN / HOLD** — mirroring the firmware's two real digital outputs, `DO_Motor_Unwind` and `DO_Motor_Wind` (`cablereel_signals.xml`). HOLD is not its own signal: it's the implicit state when both outputs are low, exactly as the hardware behaves, so it's derived rather than invented.

The active states **flash at the real PWM period** (1000 ms, `Deflection_Trim_PWMPeriod_ms`) with on-time equal to the duty cycle. That's not decoration — the reel motor has no analog speed input, so these digital outputs genuinely are pulsed at that period, and the duty cycle *is* how reel speed is modulated. A low duty visibly blinks briefly; 100% sits solid. Verified: at 12% duty the indicator measured lit on 0.17 of samples; at rest it is steady on.

**Reaching a non-HOLD state takes more than moving a slider.** Three gates in series: the published vector must clear its deadzone (X past 18°, Y past 63°), then the EMA-smoothed contribution must ramp up, then it must exceed the 0.10 discard threshold. Measured thresholds:

| State | Condition | Notes |
|---|---|---|
| UNREEL | Y ≳ 64°, or X ≳ 19° | X is absolute, so either direction only pays out |
| REEL IN | Y ≲ −165° | narrow window — see below |
| HOLD | everything else | |

REEL IN is only reachable in roughly a 15° window (−165° to −179°). At −160° the contribution is −0.0994, just under the 0.10 discard threshold; and −180° wraps to exactly +180° (same absolute encoder position), reading +1000. This narrowness is a real consequence of the config, not a sim artifact — worth raising alongside the ±350 Y deadzone question.

**Bug fixed alongside this:** the slider listeners were bound as `addEventListener('input', render)`, capturing the original `render` by reference. `render` is reassigned further down to a wrapper that also refreshes `currentVX`/`currentVY` — the values the reel-trim loop reads — so slider moves only ever called the unwrapped version and those stayed 0. Now bound as `() => render()`, which defers the lookup to call time.

> Testing note: `requestAnimationFrame` is paused in a non-fronted browser tab, which halts `stepReelTrim` entirely and freezes every value it writes. When verifying this panel through automation, front the tab first (`tabs_select`) — otherwise a dead loop looks exactly like a logic bug.

Encoder mount points inside the inner yoke, and the P-series positioning-element bracket details, still aren't modeled — see the QR24 section below for what's real vs. placeholder there.

## Structure

- `step/` — STEP exports (neutral exchange format, authoritative geometry) — from `generate_model.py`, placeholder shapes
- `stl/` — STL exports (for viewing/printing/reference) — from `generate_model.py`, placeholder shapes
- `cad/` — real, externally-authored STL parts (frame, outer yoke, inner yoke) — see above
- `docs/` — supporting notes, datasheets, reference images, and `gimbal_axis_simulator.html`
- `scripts/generate_model.py` — parametric CadQuery script that builds the placeholder assembly below (`py -3 scripts/generate_model.py`, needs `pip install -r requirements.txt`)
- `scripts/reel_inertia_model.py` — cable reel moment-of-inertia model, as a function of spooled cable length (`py -3 scripts/reel_inertia_model.py`). See "Reel inertia model" below.
- `scripts/find_bosses.py`, `scripts/render_combined.py` — derivation/verification tools for the real yoke CAD's pivot alignment (see above)
- `renders/` — matplotlib sanity-check renders (STL screenshots, the inertia-vs-length plot, the combined yoke check)

## Running the simulator

`docs/gimbal_axis_simulator.html` now fetches the real yoke STLs at runtime, so it needs to be served rather than opened directly (`file://` blocks the fetch via CORS in most browsers):

```
py -3 -m http.server 8000
```
...run from the repo root (`inreel-cad/`, not `docs/`), then open `http://localhost:8000/docs/gimbal_axis_simulator.html`.

## Reel inertia model

`scripts/reel_inertia_model.py` computes the cable reel's moment of inertia **as a function of spooled cable length**, `I(L)` — inertia (and required motor torque) changes continuously as cable winds on/off and the wound radius grows/shrinks, so a single static number isn't enough for control tuning.

Extends the TU Delft Design Report's sum-of-hollow-cylinders method (`I = ½m(r₁²+r₂²)` per component: collector + flange + drum + wound cable), which produced a single static I=0.032 kg·m² for their small 12V prototype motor and demo cable — that number doesn't transfer to the real Sandvik rig (different cable, different drum, different motor), so this model uses the real drum geometry and real Nexans cable spec instead:

| Input | Value | Source |
|---|---|---|
| Cable | 36-517-002 (2 AWG SHD-GC), 4.21 kg/m, 53.8mm OD | Nexans AmerCable Tiger Brand 36-517 datasheet |
| Drum core diameter | 62 in (Ø1.575 m) | Real Sandvik reel spec |
| Drum width | 72.25 in (1.835 m) | Real Sandvik reel spec |
| Flange diameter | 72 in (Ø1.829 m) | Real Sandvik reel spec |
| Core/flange mass | Estimated (steel, 25mm wall, 7850 kg/m³) | **Not spec'd yet** — replace with real weights if available |

Two independent methods are computed and cross-checked (agree to ~0.03% at the real geometry): a discrete layer-by-layer sum (primary, physically accurate) and a closed-form continuous-annulus approximation (fast sanity check). `max_cable_length()` is derived from the real geometry + cable OD rather than needing a separate capacity spec — comes out to ~359m for this cable/drum.

**Not yet available:** motor/gearbox ratio + rotor inertia, needed to reflect `I(L)` through to the motor shaft (`I/N² + I_motor_rotor`) for actual torque/control-tuning work — the function signature leaves room for it once that spec exists.
